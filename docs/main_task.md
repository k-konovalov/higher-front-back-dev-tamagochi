## Проектная работа «Тамагочи»

Проходной балл проекта **«Тамагочи» — 4 балла**. После его получения проект нельзя будет сдать на дополнительную итерацию ревью.

Вам предстоит написать на Python легендарную игру «Тамагочи». Её можно написать по-разному, но ваше решение должно быть реализовано на принципах ООП.

Ваша задача — реализовать часть логики игры, написать необходимые классы и имплементировать методы.

## Описание проекта

У нас будет не совсем обычный «Тамагочи», а модифицированный и немного осовремененный (Ubisoft бы позавидовала). Главное отличие — IDLE-механика, которая будет обеспечивать игре динамику. Суть игры в том, что мы создаём питомца (кто это и как его зовут, решать вам) и затем следим за его здоровьем, кормим и укладываем спать — но для всех этих действий требуются деньги. Деньги можно заработать кликом или работой. Таким образом, получается полутамагочи-полукликер.

## Правила игры

- У питомца есть несколько показателей: голод, усталость, здоровье и энергия.
- Питомец может заболеть, это влияет на его здоровье и усталость.
- При падении здоровья ниже 0 игра заканчивается.
- Каждое действие влечёт за собой изменение какого-либо состояния питомца. Например, если мы кормим питомца, то у него уменьшается голод, но может уменьшиться и энергия.

## Общая логика и компоненты игры

Сначала мы будем писать основную логику игры, никак не привязываясь к тому, где и как она будет работать (с красивой графикой, в окне или в консоли и т. д.). Игра будет разделена на несколько компонентов и сущностей:

- Питомец (тамагочи) — отвечает за логику, связанную с питомцем.
- Еда — содержит данные о конкретной еде и её стоимости, применяется для кормления питомца.
- Лекарство — содержит данные о лекарстве и его стоимости, применяется для лечения питомца.
- Кликер — логика игры, отвечающая за получение монеток, которые можно потратить на еду и лекарства.
- Сущность игры — содержит логику по запуску игры, следит за её состоянием и при наличии соответствующих условий завершает её.

Отдельно стоит обсудить взаимодействие этих компонентов. Игра при этом не знает, что происходит при выполнении того или иного действия, но может знать, какие параметры передаются и что ожидается на выходе функций. За саму реализацию уже отвечают конкретные компоненты, они управляют сущностями питомца и осуществляют менеджмент ресурсов (лекарство, еда, деньги).

## Классы, методы, функции, игровой цикл

Весь код проекта разбит на классы. Для основных сущностей определены интерфейсы, которые вы должны будете реализовать в своей игре. Давайте разберём основные сущности и интерфейсы.

1. `AbstractClicker` — интерфейс для кликера.
	Методы:
	- `def click(self) -> None:` — основная логика кликера.
		- `def __init__(self) -> None:` — инициализация кликера.
		- `def income_per_click(self) → int` — свойство для доступа к количеству заработанных монет.
2. `AbstractGame` — интерфейс для сущности игры.
	Методы:
	- `def __init__(self, tamagochi: AbstractTamagochi, clicker: AbstractClicker, all_food: list[Food], all_medicine: list[Medicine]):` — инициализация игры.
		- `def work(self) → int:` — логика действия «пойти на работу». Внутри этого метода должен использоваться кликер, который отвечает за получение монеток.
		- `def buy_food(self):` — логика действия «покупка еды».
		- `def buy_medicine(self):` — логика действия «купить лекарство».
		- `def feed_tamagochi(self):` — логика действия «покормить питомца».
		- `def heal_tamagochi(self):` — логика действия «вылечить питомца».
		- `def rest_tamagochi(self):` — логика действия «отдохнуть».
		- `def play_with_tamagochi(self):` — логика действия «поиграть с питомцем».
		- `def get_status(self):` — получение статуса игры.
		- `def food(self) -> list[Food]:` — свойство для доступа к еде.
		- `def medicine(self) -> list[Medicine]:` — свойство для доступа к лекарствам.
3. `Food` — класс-модель для представления еды.
	Поля-атрибуты:
	- `name: str` — наименование еды.
		- `satiety: int` — сколько насыщения даёт еда.
		- `price: int` — стоимость еды.
4. `Medicine` — класс-модель для представления лекарства.
	Поля-атрибуты:
	- `name: str` — наименование лекарства.
		- `price: int` — стоимость лекарства.
		- `heal_hp: int` — сколько лечит здоровья.
		- `number_of_uses: int` — максимальное количество использований лекарства.
		- `uses: int = 0` — текущее количество использований. Не может быть больше `number_of_uses`. Методы:
		- `def is_empty(self) -> bool:` — логика проверки, остались ли ещё использования лекарства.
5. `AbstractTamagochi` — интерфейс для тамагочи.
	Методы:
	- `def feed(self, food: Food) -> None:` — накормить питомца.
		- `def play(self) -> None:` — поиграть с питомцем.
		- `def rest(self) -> None:` — отдохнуть.
		- `def heal(self, medicine: Medicine) -> None:` — вылечить питомца.
		- `def status(self) -> dict[str, int]:` — получить данные обо всех показателях питомца.
		- `def is_alive(self) -> bool:` — метод для проверки, жив ли питомец.
		- `def is_sick(self) -> bool:` — метод для проверки, болен ли питомец.
		- `def update(self) -> None:` — метод для обновления состояния питомца. Должен вызываться каждый тик (или каждое действие).

## Реализация интерфейсов

Выше были описаны интерфейсы для всех нужных нам сущностей. Но что же с ними делать, как писать игру?

Ответ прост: нужно вспомнить ООП и создать для каждого из интерфейсов класс-наследник. В наследнике должны переопределяться все требуемые методы с конкретной реализацией логики.

Простой пример кликера, который ничего не делает, но выводит в консоль свои действия:

PYTHON

```python
class DummyClicker(AbstractClicker):
    def __init__(self, income_per_click: int) -> None:
        self._income_per_click = income_per_click
    
    def income_per_click(self) -> int:
        return self._income_per_click

    def click(self) -> None:
        print(f'Клик. Заработано {self.income_per_click} монет')
```

Стоит отдельно сказать, что описанные выше методы — это минимум. Никто не запрещает добавить дополнительной логики, а также разбивать логику на мелкие части. Главное — правильно реализовать тестируемый функционал, а сама реализация зависит полностью от вас.

## Запуск игры

Для того чтобы запустить игру, достаточно просто выполнить скрипт точки входа:

BASH

```bash
python main.py
```

Сам скрипт игры для запуска в консоли выглядит следующим образом:

PYTHON

```python
import os

from game.tamagochi import SimpleTamagochi  # пример названия для реализации
from game.clicker import SimpleRandomClicker # пример названия для реализации
from game.game import SimpleGame # пример названия для реализации
from game.models import Food, Medicine

def main():
    all_food = [
        Food(name='Бургер', satiety=20, price=40),
        Food(name='Салат', satiety=10, price=20),
        Food(name='Яблоко', satiety=10, price=15)
    ]

    all_medicine = [
        Medicine(name='Ибупрофен', price=30, heal_hp=20, number_of_uses=2)
    ]

    tamagochi = SimpleTamagochi()  #  Вместо SimpleTamagochi импортируйте и создайте инстанс от своей реализации
    clicker = SimpleRandomClicker(10, 20) #  Вместо SimpleRandomClicker импортируйте и создайте инстанс от своей реализации
    game = SimpleGame(tamagochi, clicker, all_food=all_food, all_medicine=all_medicine) #  Вместо SimpleGame импортируйте и создайте инстанс от своей реализации

    print("Добро пожаловать в тамагочи-кликер!")
    output = ''

    while True:
        print(output)

        print(f"Сумка с едой: {game.food}")
        print(f"Сумка с лекарствами: {game.medicine}")

        status = game.get_status()
        print(
            f"\nСтатус: голод {status['hunger']}, здоровье {status['hp']}, "
            f"энергия {status['energy']}, монет {status['coins']}\n"
        )
        if game.tamagochi.is_sick():
            print("=======Тамагочи болеет======")
            print("=======Отдых действует менее эффективно=======")
        print("1. Пойти на работу")
        print("2. Купить еду")
        print("3. Купить лекарство")
        print("4. Покормить")
        print("5. Вылечить")
        print("6. Играть")
        print("7. Отдых")
        print("0. Выход")

        match input("Выберите действие: "):
            case "1":
                income = game.work()
                output = f'Вы заработали {income} монет'
                game.tamagochi.update()
            case "2":
                game.buy_food()
            case "3":
                game.buy_medicine()
            case "4":
                game.feed_tamagochi()

            case "5":
                game.heal_tamagochi()
            case "6":
                game.play_with_tamagochi()
                output = 'Вы поиграли с питомцем'
            case "7":
                game.rest_tamagochi()
                output = 'Питомец отдохнул'
            case "0":
                break
            case _:
                output = "Неверная команда"

        os.system('clear')

if __name__ == "__main__":
    main()
```

Вместо `SimpleTamagochi`, `SimpleRandomClicker` и `SimpleGame` будут ваши классы со своей логикой. Однако благодаря тому, что они будут соответствовать интерфейсам, мы можем ожидать от них конкретных функций. При этом, если мы захотим написать новую логику в новом классе, при удовлетворении интерфейса этот же скрипт будет работать так же, как и ожидается!

### Инструкция по настройке рабочего окружения

Этот шаблон проекта использует фреймворк для тестов `pytest` и линтеры `ruff` и `flake8`. Эта инструкция поможет вам настроить рабочее окружение и установить все необходимые инструменты.

#### 1\. Создание виртуального окружения

Сначала создайте виртуальное окружение с помощью стандартного модуля Python `venv`. Выполните в терминале следующую команду, находясь в корневой папке проекта:

BASH

```bash
python -m venv .venv
```

Эта команда создаст директорию `.venv`, в которой будет находиться изолированное окружение для вашего проекта.

#### 2\. Активация виртуального окружения

Перед установкой зависимостей необходимо активировать созданное окружение. Команда зависит от вашей операционной системы и командной оболочки.

**macOS / Linux (bash, zsh):**

BASH

```bash
source .venv/bin/activate
```

**Windows (PowerShell):**

POWERSHELL

```powershell
.venv\Scripts\Activate.ps1
```

> **Примечание:** Если в PowerShell возникает ошибка выполнения скриптов, выполните команду `Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope Process` и повторите активацию.

**Windows (Command Prompt, cmd.exe):**

BATCH

```batch
.venv\Scripts\activate.bat
```

После успешной активации в начале строки вашего терминала появится префикс `(.venv)`, указывающий, что вы работаете внутри виртуального окружения.

#### 3\. Установка зависимостей

Убедитесь, что виртуальное окружение активировано. Затем установите все необходимые пакеты из файла `requirements.txt` с помощью `pip`:

BASH

```bash

```

Чтобы проверить список пакетов, установленных в виртуальное окружение, используйте команду:

BASH

```bash

```

## Чек-лист

В чек-листе мы собрали требования, которые нужно соблюсти, чтобы получить оценку за работу. При проверке ревьюер будет ориентироваться на них. Внимательно изучите их до начала работы — и затем сверьтесь по ним перед сдачей.

#### ООП

- Для всех базовых компонентов проекта созданы классы-наследники от абстрактных классов.
- Все необходимые методы абстрактных классов реализованы в наследниках и соответствуют контракту (правильная сигнатура функций).
- Логика каждого компонента находится на своём месте (то есть класс кликера отвечает только за логику кликера, класс питомца — только за логику питомца и т. п.).
- Клиентский код работает только с контрактом и не зависит от реализации (скрипт [main.py](http://main.py/) работает с любой из реализаций и не знает её логику, а опирается на абстракцию).

#### Логика игры и работа с ЯП

- Код успешно запускается, нет внештатных завершений с ошибками.
- Соблюдены и реализуются все правила игры.
- В игре есть несколько состояний, есть конец игры.
- Каждый цикл хода игры меняется общее состояние, в зависимости от выбранного действия.
- Код должен работать без сторонних (не включённых в стандартную библиотеку) зависимостей.

#### Code style

- Линтер не обнаруживает ошибок.
- Имена методов и переменных понятные и отражают суть хранящихся в них данных.
- Для каждого метода написана docstring с описанием метода, принимаемыми аргументами, возвращаемым значением и возможными исключениями (если предполагаются).
- Для аргументов каждого метода проставлены подсказки типов, а также для возвращаемого значения.
- Допускаются комментарии к коду, но сам по себе код должен читаться без труда.
